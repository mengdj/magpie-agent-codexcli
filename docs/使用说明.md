# magpie-agent-codex-cli 使用说明

把 **Codex CLI**（终端里的 `codex` 控制台，以及 `codex exec`）接到 magpie：
在 magpie 的 Agent 页给它挑一个模型，然后在终端用 `codex-magpie` 启动，
模型请求就经由 magpie 的网关，走你已登录的订阅。

适用于 **Codex CLI**，不是 Codex 桌面版。

---

## 一、它解决什么问题

magpie 的 Agent 插件只能把模型和连接信息写进 **JSON / YAML / ENV** 三种文件，
而 Codex CLI 的配置是 **TOML**（`~/.codex/config.toml`）。直接声明 TOML 会被 magpie 拒绝：

```
agent.format "toml": json, yaml or env
```

所以分工是这样的：

```
magpie（只写它能写的）
  └─> ~/.codex/magpie-codex-cli.env
        CODEX_MODEL=auto/hy3
        CODEX_BASE_URL=http://127.0.0.1:3425/v1
        CODEX_API_KEY=magpie-codex-cli
              │
              │  插件负责转换
              ▼
codex-magpie ──> codex -c model=... -c model_providers.magpie.base_url=...
```

- **magpie 管 env 文件**：选模型、换账号、在 Agent 页关掉时整行恢复，都是 magpie 自己的机制。
- **插件管 TOML 那一侧**：转换、备份、还原。

好处是模型、网关地址、密钥只有一份来源，不需要你手工抄进 `config.toml`。

## 二、安装

### 1. 装插件

```bash
magpie plugin add ./magpie-agent-codexcli
# 或从仓库
magpie plugin add git+https://gitee.com/mengdj/magpie-agent-codexcli.git
```

装好之后 magpie 的 **Agent** 页会多一行 `Codex CLI`，带自己的图标
（深色终端底 + 白色 `>` + 绿色光标）。图标是内联 SVG，不联网。

命令行也能确认：

```bash
magpie ls            # 列表里出现 Codex CLI
magpie codex-cli     # 只看这一行
```

### 2. 给 Codex CLI 选一个模型

两种方式，选一种：

- 在 magpie 窗口的 **Agent** 页，点 `Codex CLI` 那一行的模型选择器；
- 命令行：

  ```bash
  magpie models codex-cli          # 看可选模型
  magpie codex-cli auto/hy3        # 选一个
  ```

选完会写出 `~/.codex/magpie-codex-cli.env`。

### 3. 让 `codex-magpie` 能直接敲

`magpie plugin add` **不会**执行 npm 安装，也不会创建全局命令——它只是把插件登记给
magpie 自己用。所以这一步要你自己做一次：

```bash
cd magpie-agent-codexcli
node bin/setup.mjs
```

它会往 npm 的全局 bin 目录里放 3 个很小的转发文件
（`codex-magpie`、`codex-magpie.cmd`、`codex-magpie.ps1`），内容指向本目录的
`bin/codex-magpie.mjs`。

> 这些文件**不会**出现在 `npm ls -g` 里，不是全局 npm 包。
> 挪动了插件目录之后，重新跑一次即可。

相关命令：

```bash
node bin/setup.mjs --print-dir   # 只看会写到哪里
node bin/setup.mjs --uninstall   # 只删它自己写的文件
```

不想装也可以，直接用完整路径：

```powershell
node D:\magpie\magpie-agent-codexcli\bin\codex-magpie.mjs
```

## 三、日常使用

### 启动控制台

```bash
codex-magpie
```

打开的仍然是原生的 Codex CLI 控制台，只是模型走 magpie。界面上会显示模型名，
例如 `Hy3 · routing group low`。

想切回原来的配置，直接敲 `codex` 就行——两者互不影响。

### 非交互执行

```bash
codex-magpie exec --skip-git-repo-check "把测试跑一遍"
```

### 其余参数原样透传

插件只认 5 个子命令（见下一节），**其余参数一律拼在注入的 `-c` 后面交给 codex**，
所以 codex 自己的开关都能用：

```bash
codex-magpie --yolo                        # 同 codex --yolo
codex-magpie resume --last                 # 继续上次会话
codex-magpie -m auto/deepseek-v4.1-flash   # 临时换一个 magpie 模型
```

带空格和引号的参数会完整保留（Windows 下 `.cmd` 走 shell 时会重新加引号）。
你自己传的 `-m` / `-c` 排在后面，会覆盖插件注入的值，适合临时试验。

## 四、命令一览

| 命令 | 作用 |
|---|---|
| `codex-magpie [参数...]` | 用 magpie 的模型启动 Codex（**不修改任何文件**） |
| `codex-magpie install` | 把配置写进 `config.toml`，并记录可还原的日志 |
| `codex-magpie restore` | 按日志把 `config.toml` 还原 |
| `codex-magpie status` | 看 magpie 选了什么、Codex 现在读的是什么 |
| `codex-magpie which` | 打印实际会调用的 codex 可执行文件 |
| `codex-magpie help` | 简短帮助 |

### `status` 怎么看

```
CODEX_HOME           C:\Users\you\.codex
model                auto/qfmodel          ← magpie 选的值
in effect            auto/qfmodel          ← 实际生效的值（仅在两边不一致时出现）
gateway              http://127.0.0.1:3425/v1
env file             ...\magpie-codex-cli.env
model catalog        ...\magpie-models.json
config.toml          ...\config.toml
config model         auto/qfmodel
config provider      magpie
config→this key      no (not installed)     ← 只有 install 之后才会是 yes
journal              6 keys (restore available)
```

`config→this key` 指的是 `config.toml` 里存的是不是本插件的密钥。
默认模式（`-c` 覆盖）下它是 `no`，属正常现象，不影响使用。

## 五、两种接入方式

### 方式 A（推荐）：不碰配置文件

`codex-magpie` 用 Codex 的 `-c key=value` 覆盖参数启动，**完全不写** `config.toml`：

```bash
codex-magpie   # 走 magpie
codex          # 还是你原来的配置
```

适合日常在终端里用。缺点是只对你手动敲的命令生效。

### 方式 B：写进 config.toml

有些场景读不到你敲的命令行参数，比如 IDE 插件、`codex app-server`、
或者别的工具替你启动 codex。这时用：

```bash
codex-magpie install
```

它只改自己负责的 6 个键，其余内容、注释、顺序一律保留：

| 键 | 值 |
|---|---|
| `model` | magpie 里选的模型 |
| `model_provider` | `magpie` |
| `model_providers.magpie.name` | `magpie` |
| `model_providers.magpie.base_url` | 网关 `/v1` 地址 |
| `model_providers.magpie.wire_api` | `responses` |
| `model_providers.magpie.experimental_bearer_token` | 这个 Agent 自己的网关密钥 |

还原：

```bash
codex-magpie restore
```

写之前它会把每个键的**原始值（含行尾注释）**记进
`~/.codex/magpie-codex-cli.journal.json`；`restore` 按这份日志逐行放回，
原来不存在的键会被删掉，所以能还原到**逐字节一致**。

## 六、两边换模型都不会互相覆盖

有两个地方能换模型：

1. magpie 的 Agent 页（写 `magpie-codex-cli.env`）
2. Codex 自己的 `/model`（写 `config.toml`）

插件按 **谁最后改就用谁** 协调（比较两个文件的修改时间），并把结果同步到另一边：

```
在 magpie 里选  → env 更新  → 启动时把 config.toml 的 model 对齐
在 TUI 里 /model 回车 → config.toml 更新 → 启动时写回 env，Agents 页跟着变
```

同步发生时启动器会打一行提示，例如：

```
codex-magpie: synced env: CODEX_MODEL=workbuddy/glm-5.3-flash
```

**注意 TUI 里的两个键**：

- 按 `s` → 只影响当前会话，不动默认值；
- 按回车 → 写进默认值，下次启动仍用它。

## 八、常见问题

**Q：敲 `codex-magpie` 提示找不到命令？**
还没做第二节第 3 步。跑一次 `node bin/setup.mjs`，然后**新开一个终端**
（PATH 在 shell 启动时读取）。

**Q：提示 `magpie has not chosen a model for Codex CLI`？**
还没选模型。去 magpie 的 Agent 页选，或 `magpie codex-cli <provider>/<model>`。

**Q：换了模型但没生效？**
先看 `codex-magpie status`。如果 `model` 和 `in effect` 不同，说明另一边更新，
启动时会自动同步。若仍不对，检查是否在 TUI 里按的是 `s`（仅本会话）而不是回车。

**Q：会不会和 magpie 内置的 `Codex` 行冲突？**
内置的 `Codex` 行也在写 `config.toml`。方式 A 完全不碰那个文件，所以不冲突。
只有用了 `install` 之后，再从 magpie 内置 Codex 行换模型会覆盖掉——
`codex-magpie status` 会提示这种情况。

**Q：请求走哪里？计费算谁的？**
`codex-magpie` 不代理请求，只是把模型和网关以 Codex 自己的方式传进去，
请求由 Codex 直接发往 magpie 网关。每请求计入该 Agent 自己的 key，
magpie 的 Usage 里能按 `Codex CLI` 区分。

**Q：想彻底卸载？**

```bash
node bin/setup.mjs --uninstall   # 删命令
magpie plugin rm magpie-agent-codexcli   # 删插件
codex-magpie restore             # 如果用过 install，先还原
```

## 九、支持平台

Windows、Linux、macOS 都支持，不额外依赖（只要 Node 18+ 和可用的 `codex`）。

| 项目 | Windows | Linux / macOS |
|---|---|---|
| 找 `codex` | `codex.exe` → `.cmd` → `.bat` → `codex` | PATH 里第一个 `codex`（排除本插件的 shim） |
| 启动方式 | `.cmd`/`.bat` 走 shell，其余直接 spawn | 直接 spawn，不加 shell |
| Ctrl-C | 转发 `SIGINT` 给子进程 | 同左，并按 `128+N` 返回（130/143/129） |
| `setup.mjs` 写到哪 | `npm prefix -g`（通常 `%APPDATA%\npm`） | `npm prefix -g` + `/bin`，找不到则 `~/.local/bin` |
| 生成的 shim | `codex-magpie` + `.cmd` + `.ps1` | 单个 `codex-magpie`（`0755`） |

已知差异：Windows 上 `process.kill(pid,'SIGTERM')` 会映射成 `TerminateProcess`，
退出码是 `1` 而不是 `143`；只是回显差异，进程不会卡住。

> 说明：Windows 已实测通过；Linux/macOS 的平台分支有单元测试覆盖，
> 但未在真机上跑过完整端到端。

## 十、文件位置

| 文件 | 说明 |
|---|---|
| `~/.codex/magpie-codex-cli.env` | magpie 写，模型/网关/密钥的来源 |
| `~/.codex/config.toml` | Codex 自己的配置；只有 `install` 才会改 |
| `~/.codex/magpie-codex-cli.journal.json` | `install` 的还原日志，`restore` 后自动删除 |
| `~/.codex/magpie-models.json` | magpie 的模型目录（上下文窗口等），启动时一并带上 |
